## 修订前的局部基础与行为

[架构说明](architecture.md) 将产品职责描述为把人的决定变成环境约束，使偏离不能静默发生或被掩盖。[README](../README.md) 把未经计划审查时阻止实施作为产品的核心演示。[既有 ratified decision](decisions/d-gate-governs-git-product.md) 明确要求产品代码在计划批准后才能写入。

这些材料支持保留“先批准计划，后实施”的既有承诺。它们不单独证明指定 reviewer、重复审查轮次或 exact-file 清单是身份级公理；也不能证明完整 review 循环是上述承诺的必然推导。历史上这些机制的基础地位和全部选择理由尚未恢复。

`2026-09-04-windows-verification` 的事件账本记录了 12 轮 plan review、5 轮 code review、17 次无 reviewer verdict 的失败，以及 7 条追加授权记录。16 次失败记录为组织级 HTTP 403，另一次因已有 skip 授权而未执行。这挑战了反复审查能够经济地推进工作的假设；它不证明一切工程错误都不收敛，也不证明所有 review 没有价值。该 Change 已归档，仅作为历史证据。

证据：[事件账本](../.harness/events.jsonl)，以及 `super-harness report --since 2026-09-03 --until 2026-09-10`。授权事件不独立证明人在场操作次数；报告中的零 reviewer token 不表示零成本。

## 已确认的基础

### 1. 计划审查是实施的前提

产品实施必须以经过 review 并获准的 plan 为前提。产品基础不统一强制 review 的具体方式。

用户确认：“底线，plan 需要 review，才能进行，至于怎么review，这个不做强要求”。这保留既有底线，并限定了可从底线推导出的要求；不自动废除项目当前已经配置的审查政策。

### 2. 批准授予边界内的自主权

批准 plan 后，agent 获得边界内自主推进的权限，包括判断并处理实施中新发现的问题、补充文件和调整实现办法。新错误、新文件或实现细节变化本身，不足以要求人重新批准。

具体确认案例：目标、方案和验收条件不变时，补充遗漏的测试 fixture 仍由原计划批准覆盖。

### 3. agent 不能自行改变人的承诺

agent 可以改变完成承诺的实现办法，不能自行改变已批准的承诺或解除明确限制。必须改变承诺或限制时，旧批准不覆盖变更部分；相应的新计划内容需要 review 获准后才能实施。

承诺包括已批准的目标、预期行为、验收义务和明确限制。关键技术方案若被明确设为限制，也属于该边界。不能仅凭文件数量、HEAD 或计划文字变化判定授权已失效。

实施中的边界判断由 agent 在获授的自主权内作出，并保留可追溯的依据。该权限不等于允许用“只是实现细节”掩盖对承诺的修改。

### 4. 产品不以反复人工许可维持正常推进

super-harness 负责批准依据与偏离的可追溯性，不承诺所有语义判断正确、工程错误修复必然收敛，或审查必然推进到通过。频繁要求人在运行中许可普通工程探索，不是正常推进方式。

需要改变人的承诺或取得新增权限时才请求相应授权；不能把每次工程发现转换成完整治理重启。

以上第 2 至第 4 项由产品决策者在讨论中以“可以”“ok”确认。本次确认建立新的产品方向，不声称这些表述在历史版本中已存在。

## 必要影响与尚未决定的机制

上述基础要求后续检查 declare、plan epoch、exact-file scope、review 编排和 report 的职责：实现变化不能被无条件等同于授权变化，批准必须提供真实的自主行动空间。

留给技术设计：批准边界的具体表示、判定记录格式，以及落实用户认可规则的核验机制。尚未选择的新政策：持续 skip、成本指标与阈值；本次交接不要求引入这些能力。可选编排不纳入本次交付义务。reviewer 调用、重试与相应故障处理由外部工作流组织，具体机制未选定。此前讨论的五项边界表未作为固定 schema 获批。

本次讨论明确的是 plan review；不据此推导取消 code review、指定替代 reviewer 或直接放宽合并条件。

## 受影响的产品契约（从已确认基础推导）

本节是方法层的必要推导与现状对照，不把新的机制选择记作用户已批准。

| 产品概念 | 必须保留的含义 | 依据 |
|---|---|---|
| 计划批准 | 对特定承诺及限制授予实施权限 | 基础 1、2、3 |
| 实现变化 | 在原承诺内完成工作的调整，不天然生成新授权需求 | 基础 2 |
| 授权变化 | 改变承诺或解除限制，旧批准不覆盖变化部分 | 基础 3 |
| 审查证据 | 说明谁或何种获认可方式审查了什么；不能虚构或扩大证据覆盖 | 基础 1、4 |
| agent 边界判断 | 实施者对变化与原批准关系的判断，保留依据；不等于新计划已获 review | 基础 2、3、4 |

### 必须调整或区分的现有行为

1. **文件范围与授权范围。** [plan CLI 的既有设计](../src/super_harness/cli/plan.py) 明确将晚期 scope 扩展送回 plan review，且有意不提供免重审的 scope 修订路径。若这种扩展只是已批准承诺内补充 fixture，它与基础 2 冲突。后续设计必须能表达并处理这种情况。精确文件清单仍可用于检查、审查目标和追溯；本推导不要求删除它。
2. **批准有效性与证据版本。** [审查契约](../src/super_harness/engineering/review_contract.py) 以准确 Git 目标和范围构造证据。准确绑定本身与新基础相容。目标变化需要刷新哪些代码证据，应与计划承诺是否变化分别判断；不能直接把两者等同。
3. **计划复审与代码复审。** [入门文档](getting-started.md) 已允许 code-only 修复通过 implementation reopen 处理而不重开计划。这种职责分离与新基础相容，应保留其产品含义；本记录不指定命令或状态机改法。
4. **review 编排的地位。** [架构说明](architecture.md) 已包含 source、冻结轮次、收集结果和预算的编排职责。这些是现有选择，不能由“计划必须 review”必然推出。产品决策者随后确认将编排移出核心职责，责任划分见下节；现有能力是否作为可选能力保留及其迁移方式尚未决定，本次确认不自动授权删除。

### 后续设计必须通过的语义场景

- 首次没有计划批准：不能开始产品实施。
- 在原目标、方案和验收条件内补充 fixture：agent 可以推进，不因文件新增要求人工重新批准。
- 多次调整累计改变已批准目标：不能仅以每一步都很小声称仍受原批准覆盖；判断要对应获批承诺。
- 通过降低验收标准消除失败：属于改变承诺，旧批准不覆盖该变化。
- rebase 只改变 Git 身份而不改变批准内容及其适用条件：不能仅因新 HEAD 宣告计划授权失效；代码验证证据另行判断。
- reviewer 不可用：不能声称获得 review 结论。采用何种其他审查或例外政策仍是独立事项，不由基础 2 自动授予 skip。

这些是结果层义务，不规定实现算法，也不证明当前版本已经满足。

## 已确认的产品职责选择：review 编排移出核心

2026-09-10，产品决策者对“将 review 编排移出核心职责”的明确提议回答“可以”。这是在多种符合基础的方案中作出的新产品职责选择（selected because），不是声称从“计划必须 review”只能推导出这一种架构。选择理由是保持批准前置与自主推进，同时避免核心产品承担组织审查及反复重试的流程责任。

| 参与方 | 责任边界 |
|---|---|
| super-harness 核心 | 接收并核验获认可的审查依据，执行批准前置条件，保留批准、适用内容及偏离的追溯关系 |
| 外部工作流 | 组织 review、调用审查者、安排重试并处理执行故障；外部工作流可以自动运行，不表示必须由人逐次操作 |
| 实施 agent | 在批准边界内推进并说明边界判断，不因承担实施责任而自动取得新计划的批准权 |

核验审查依据不等于重新执行实质 review，也不保证审查结论正确。审查流程的认可权与核验边界见下一节；不能仅凭存在一份文件就声称计划已获批准。

该选择要求核心能够在不组织 reviewer 调用与重试的情况下履行上述职责。是否另外保留可选编排能力尚未决定；不据此取消 code review、改变当前批准政策或选择替代模型。没有有效审查依据时，不能以编排已外移为由自动通过或 skip。

## 已确认的信任选择：用户预先认可审查流程

2026-09-11，产品决策者以“ok”确认：由用户预先认可审查流程，核心接受该流程的明确结论，不统一要求 reviewer 独立性或模型配置。这是新选择，不追溯改变历史审查政策。

核心核验三个方面：审查对象对应哪份计划及其批准内容；结论是否明确批准实施；该结论是否来自用户认可的流程。未完成、执行失败或没有结论均不能充当通过。实施 agent 不能自行扩大流程的认可范围。

被认可的流程可以采用人工、同一 agent 的专门审查步骤、独立 agent 或多个模型。是否要求独立审查由用户政策决定；同一 agent 只有在预先认可的流程允许时才能承担审查，实施权限本身不授予批准权。规则确定后，正常执行不需要人逐次确认。

核心信任该流程提供的审查结论，不重新评判计划质量，也不保证审查者认真思考过或结论正确。产品保证的核验范围止于对象、明确结论和来源符合认可规则。选择这一边界，是为了保留 review 前置条件，同时避免核心再次承担实质审查与审查循环。

认可规则的保存形式、来源核验机制和证据表示留给后续技术设计。迁移政策见下节；在实际切换完成前，现有独立性要求或来源限制不会因本记录自动失效。

### 交接范围与自由度

技术设计可以选择计划表示、证据表示、来源核验方法、命令和状态转换的组织方式，以及如何保存和展示边界判断。具体技术选择应满足 O1–O7，不反向增加固定 reviewer、每次变更人工审批或新的产品权限要求。

本次不新设计持续 skip、review 成本分析或可选 reviewer 编排产品，也不取消现有 code-review 和验证义务。实现审查的组织方式与 code-review 是否必须存在是不同问题：编排职责的迁出适用前者，不能被用作删除后者的依据。

来源核验有技术实现自由，但技术方案仍需明确其信任假设和可保证的范围。若发现必须改变“谁有权认可流程”、允许绕过批准或引入新的风险接受政策，需返回产品决策；不能当作实现细节自定。
